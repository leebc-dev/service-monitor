# 풋볼라운지 실제 HTTP → Gmail 검증

2026-10-14 **20:41:04–20:41:53 (한국 시간)**, 로컬 풋볼라운지와 모니터링 서버에서 검증했습니다.

## 결과

| 항목 | 관측 결과 |
|---|---|
| 실제 HTTP 요청 | 60건: 의도한 500 20건, 2초 지연 20건, 정상 응답 20건 |
| 지연 요청의 클라이언트 측 왕복 시간 | 2,007–2,024ms |
| 오류율 알림 | 1건, 최초 10건의 오류율 100%에서 생성 |
| 평균 응답 시간 알림 | 1건, 14건의 평균 약 579ms에서 생성 |
| Gmail 발송 | 두 알림 모두 첫 시도에 SMTP 접수 |
| 실제 수신 | 사용자가 두 종류 각각 1건 수신, 중복 없음 확인 |
| 동일 오류·지연 재발생 | 추가 알림 0건, 추가 이메일 작업 0건 |
| Redis 반복 억제 TTL | 오류율 약 580.5→552.7초, 지연 약 588.5→560.7초. 연장되지 않음 |
| MySQL / 실시간 지표 / 알림 소비자 | 실제 요청 60건 모두 처리 확인 |

합성 이벤트를 수신 API에 주입하지 않았습니다. 로컬 풋볼라운지의 실제 HTTP 필터 측정값이 Kafka를 거쳐 알림과 이메일로 이어지는 흐름을 검증했습니다. 운영 EC2 요청은 포함되지 않습니다.

## 재현

세 앱과 Docker 인프라, Gmail 이메일 설정이 켜져 있어야 합니다.

```bash
python3 scripts/football-alerts-live.py
```

이 명령은 설정한 수신 주소로 **실제 알림 이메일 2건**을 발송합니다. 기존 최근 5분 요청이 있거나 실제 Redis 반복 억제 시간이 남아 있으면 테스트를 시작하지 않습니다. 다른 트래픽 없이, 기존 표본과 10분 억제 시간이 자연 만료된 다음 실행합니다. 억제 키를 지우거나 알림 기준을 낮추지 않습니다.

스크립트는 500 10건과 2초 지연 10건으로 두 알림을 만든 다음 동일한 요청을 다시 보냅니다. 이어 정상 요청 20건을 보내고 소비자가 모두 처리한 뒤 알림 ID·이메일 작업 수·실제 Redis TTL이 유지되는지 확인합니다. 요청·알림 이력은 대시보드에서 볼 수 있도록 보존합니다. 기계 판독 결과는 `.runtime/football-alerts-live-result.json`에 저장합니다. 스크립트의 `SENT` 검사는 SMTP 접수이며 수신함 도착은 사용자가 확인합니다.

풋볼라운지의 `monitoring-local` 전용 경로:

```text
GET http://127.0.0.1:18090/api/v1/monitoring-demo/error
GET http://127.0.0.1:18090/api/v1/monitoring-demo/slow?delayMs=2000
```

`delayMs`는 기본 300, 허용 범위 0–3000ms입니다. 범위 밖 입력은 400으로 거절합니다. 해당 컨트롤러는 로컬 프로필에서만 등록됩니다.

10분이 지난 뒤에도 새로운 요청이 기준을 초과하면 새 알림이 가능합니다. 이번 검증은 같은 알림을 영구적으로 차단하는 것이 아니라 **억제 시간 안에 반복 발송되지 않음**을 확인합니다.
