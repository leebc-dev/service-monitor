# 알림 설정과 검증

알림 채널은 Vue 대시보드와 이메일입니다. 새 알림은 페이지가 열려 있는 동안 15초 폴링으로 배너에 표시되고 MySQL에 저장된 최근 50건을 이력에서 확인할 수 있습니다. 처음 화면을 열 때 기존 이력을 새 알림으로 다시 띄우지 않습니다. 배너 닫기는 화면 안내만 닫으며 저장된 알림과 이메일 발송에 영향을 주지 않습니다. Gmail 설정은 [이메일 가이드](email.md)에 있습니다.

## 기본 기준

| 항목 | 기본값 |
|---|---|
| 판단 구간 | 발생 시각 기준 최근 5분 |
| 최소 표본 | 10건 |
| 오류율 | HTTP 5xx 비율 10% 이상 |
| 응답 시간 | 전체 요청의 평균 처리 시간 500ms 이상 |
| 반복 억제 | 서비스·환경·알림 종류별 600초 |

두 조건은 각각 독립적입니다. 오류율과 응답 시간이 함께 높으면 두 알림을 만듭니다. HTTP 4xx는 오류율의 분자에 포함하지 않습니다. 평균 처리 시간은 동기 HTTP 필터의 측정값입니다. API별 임계치나 p95 기준은 아직 없습니다.

새 이벤트를 소비할 때 판단합니다. 억제 시간 만료 후에도 새 요청이 들어와 기준을 충족해야 재알림합니다. 요청이 없으면 주기적인 재발송을 하지 않습니다. 중간에 정상으로 회복돼도 쿨다운을 초기화하지 않으며 회복 알림은 만들지 않습니다. 5분을 넘겨 도착한 과거 이벤트로는 새 알림을 생성하지 않습니다.

## 설정 변경

프로젝트 루트 `.env`에 다음 값을 지정하고 모니터링 백엔드를 재시작합니다. 누락된 값에는 같은 기본값이 적용됩니다. 최소 표본은 1 이상, 오류율은 0.01~100%, 평균 시간은 1~3,600,000ms, 억제 시간은 1~86,400초입니다.

```dotenv
MONITOR_ALERTS_ENABLED=true
MONITOR_ALERT_MINIMUM_REQUESTS=10
MONITOR_ALERT_ERROR_RATE_PERCENT=10
MONITOR_ALERT_AVERAGE_DURATION_MS=500
MONITOR_ALERT_COOLDOWN_SECONDS=600
```

API `GET /api/v1/services/football-lounge/alerts?environment=development`와 화면에 실제 적용된 설정이 표시됩니다. 설정 변경 직전에 이미 생성된 Redis 억제 키는 기존 TTL까지 유지됩니다. 알림 비활성화 중에는 소비 오프셋이 진행되므로 활성화 후 꺼져 있던 기간의 이벤트를 소급해서 알리지 않습니다.

## 반복 억제와 실패 처리

1. `monitor-alerts-v1` 소비자는 자기 Redis 창에 이벤트를 저장합니다. 실시간 집계 소비자와 순서 경쟁을 하지 않습니다.
2. 기준을 만족하면 `monitor:{서비스:환경}:alert-cooldown:ERROR_RATE` 또는 `LATENCY` 키를 확인합니다. 키가 있으면 DB 쓰기를 생략합니다.
3. 키가 없으면 MySQL 트랜잭션에서 해당 규칙 상태 행을 잠그고 마지막 알림 시각을 확인합니다. 아직 억제 중이면 추가 알림을 저장하지 않습니다.
4. 새 알림 이력과 마지막 시각을 함께 커밋한 뒤 Redis에 `SET NX`와 남은 TTL을 설정합니다. 반복 이벤트가 TTL을 계속 연장하지 않습니다.
5. Redis 키 유실이나 DB 커밋 직후 프로세스 종료가 발생해도 MySQL 상태가 중복을 막습니다. 같은 원인 이벤트 재처리는 결정적인 알림 ID로 추가 저장을 막습니다.

DB 저장 실패 시 억제 키를 만들지 않고 Kafka에서 재시도합니다. Redis 장애도 알림 소비자가 재시도하며 이력 저장 소비자는 독립적으로 동작합니다. 이메일이 켜져 있으면 알림과 발송 작업을 같은 DB 트랜잭션에 저장합니다. SMTP 오류는 별도 메일 작업자가 재시도하므로 Kafka 알림 판단을 멈추지 않습니다. Redis와 MySQL을 하나의 분산 트랜잭션으로 묶거나 SMTP 전달까지 정확히 한 번 처리된다고 보장하는 구현은 아닙니다.

## 자동 검증

실제 풋볼라운지 HTTP 오류·지연에서 Gmail 수신까지 확인하려면 [실제 HTTP 알림 테스트](live-alert-test.md)의 `scripts/football-alerts-live.py`를 사용합니다. 실제 알림 2건과 반복 억제를 검증한 기록이 있습니다.

화면에서 직접 확인하려면 풋볼라운지 로컬 서버까지 켠 다음 실행합니다.

```bash
python3 scripts/alerts-demo.py
```

로컬 풋볼라운지의 테스트 API에 의도한 500 요청을 10번 보내고, 응답 시간 알림 시연을 위해 `synthetic-alert-demo` 버전의 합성 2,000ms 이벤트를 10건 주입합니다. 후자는 실제 지연을 측정한 데이터가 아닙니다. 이메일이 켜져 있으면 실제 수신 주소로 메일도 보낼 수 있습니다. 이미 억제 중이거나 다른 요청이 많은 경우 새 알림이 발생하지 않을 수 있습니다. 데모 이력은 화면에서 확인할 수 있도록 남깁니다.

MySQL·Redis·Kafka와 모니터링 백엔드가 실행되고 이메일이 꺼진 상태에서:

```bash
python3 scripts/alerts-e2e.py
```

고유한 테스트 서비스 2개를 잠시 등록해 최소 표본, 두 임계치, 이벤트 재전송, 연속 초과 시 반복 억제, 서비스별 독립성, Redis 키 유실 후 복원을 확인합니다. 이메일이 켜져 있으면 외부 발송을 피하기 위해 중단하므로 로컬 SMTP를 사용하는 `scripts/email-e2e.py`를 사용하세요. 끝나면 해당 실행에서 만든 DB·Redis 데이터만 정리합니다. Kafka 테스트 이벤트는 토픽 보존 정책에 따라 남습니다.

실제 TTL 만료까지 빠르게 검증하려면 기존 백엔드를 종료하고 별도 터미널에서 짧은 값을 적용합니다.

```bash
MONITOR_ALERT_COOLDOWN_SECONDS=8 ./scripts/backend.sh
```

```bash
python3 scripts/alerts-e2e.py --verify-cooldown
```

완료 후 짧은 설정으로 실행한 백엔드를 종료하고 `./scripts/backend.sh`로 재실행하면 `.env`/기본 설정으로 돌아옵니다. 이 테스트는 기본 임계치(10건, 10%, 500ms)를 전제로 합니다.

2026-10-14 검증: 알림 단위 테스트 12개, 기존 지표 테스트 2개, Vue 타입 검사·빌드 통과. 실제 Kafka·MySQL·Redis에서 두 알림 생성, 반복 억제, 키 유실 복구, 실제 TTL 만료 후 재알림, 다른 소비자 정상 처리까지 통과했습니다.
